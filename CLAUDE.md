# WaaS dashboard: agent guide

@AGENTS.md

The AnyPress dashboard (app.anypress.io): a Next.js app that manages everything the provisioning API runs. It has no database of its own; every read and write goes through the API, which also runs sign-in (Better Auth, passed through at `/api/auth/*`) and decides what each person may see.

- Before pushing, run what CI runs: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run deadcode`, `npm test`, `npm run build`. `npm run deadcode` (Fallow, `.fallowrc.json`) fails on unused files, exports, types and packages: remove them rather than ignoring them. On a pull request CI also runs `fallow audit`, which fails on duplicated or overly complex code the change adds.
- The look is in `DESIGN.md` (quiet, neutral, data-first, shadcn/ui components in `components/`). Follow its tokens; don't add colours or a second component kit.
- A change that needs a new API route goes into `waas-provisioning-api` first (with its OpenAPI entry), then here.
- Merging doesn't always reach app.anypress.io: after a merge, check the live deployment is on the new commit.

## Rules for every change

- **Playground only for tests.** Never create a store, product (seller), reseller or ready-made storefront on the server to try, check or demo something. Check on WordPress Playground (the WordPress skills in `.claude/skills/`, and the plugins repo's `scripts/playground`). The API's own tests cover the server building stores. If a check truly can't run on Playground, ask the owner first, say why, and delete the store as soon as the check is done. Never keep test stores.
- **Store tests run as a site type.** Every Playground test, preview or screenshot of a customer store is one of the store template's site types (the keys of `waas-provisioning-api/templates/anypress-store/roles.json`: website, bookings, online-store, community, everything, highlevel), with AnyPress Client on and `ANYPRESS_TENANT_ROLES` set, so only that type's plugins are on, as on a real store. Never a WordPress with every plugin on and no site type. Say which site type in the report or screenshot.
- **Beads, every time.** Each piece of work gets a Beads issue in the list of the repository it changes, before it starts (check for a duplicate first). Put the id in the branch, the PR and the status, and close the issue when the PR merges or the change is live. Run `bd` in the session doing the work; the SessionStart hook in `.claude/settings.json` loads the Dolt login and sets up `.beads` from DoltHub, then `bd dolt push` syncs it. This repository's issues are in DoltHub `chowderr/waas_dashboard` (new ids `dashboard-*`; issues moved here from another list keep their old ids). Each AnyPress repository has its own list. Work that also changes another repository gets an `also:<repo>` label (`api`, `plugins`, `dashboard`, `site`, `theme`, `blocks`, `fluentsuite`), and a task whose epic is in another list gets `epic:<id>`. Jobs that change no code (accounts, outreach, server and shop settings) go in AnyPress Ops (`chowderr/anypress_ops`, in the obsidian-vault repository under `1. Projects/WaaS/AnyPress Ops/`).
- **Pull requests:** open them ready for review, not as drafts, so CI runs. Merge a PR yourself once CI is green and the work was asked for.
- **No "WPCS" wording.** The old platform is gone. Say "the AnyPress API" or "the API's key and secret login". Don't add the word anywhere.
- **Public docs are for users.** READMEs and `docs/` explain how to use and run the code. Internal notes (server and Coolify ids, Beads, deployment steps) go in the obsidian-vault repository under `1. Projects/WaaS/`. Never put how or why AnyPress started in public copy.
- **Official SDKs, always.** Call every outside service through its official SDK or library and configure it to fit (custom storage, base URL, options), rather than writing the HTTP calls by hand. Read the SDK's options before deciding it doesn't fit. Only where no official SDK exists, write the client yourself and say so in the PR.
- **Verify before claiming.** Check npm, wordpress.org or the official docs before calling a version or spec "the latest", and check a fix on the running system before calling it fixed.
